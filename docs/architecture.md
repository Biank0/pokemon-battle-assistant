# 技术架构规划

## 总体架构

```text
用户输入
  ↓
Bot 接入层
  ↓
输入解析 / 标准化
  ↓
局面状态模型 Battle State
  ↓
规则与知识层
  ↓
模拟与评估层
  ↓
博弈推理层
  ↓
自然语言解释层
  ↓
用户输出
```

## 模块设计

### 1. Bot 接入层 `bot/`

负责接收用户输入和返回结果。

初期建议：

- CLI 命令行入口
- JSON 输入 / 输出

后续可扩展：

- Web API
- Discord / Telegram / 飞书机器人
- 网页可视化对战助手

### 2. 对战状态层 `battle/`

核心对象：

- `PokemonSet`：宝可梦配置，包括种族、招式、道具、特性、性格、努力值等
- `Team`：队伍
- `BattleState`：当前局面，包括在场宝可梦、天气、场地、钉子、状态等
- `Action`：可选操作，包括出招、换人、太晶 / 极巨 / Mega 等特殊机制
- `TurnResult`：模拟后的结果

### 3. 知识层 `knowledge/`

存放静态知识与规则：

- 属性克制表
- 招式数据
- 特性数据
- 道具数据
- 常见配置模板
- 环境威胁列表
- 规则集配置

初期可以用小型 YAML / JSON 文件维护，后期替换为完整数据源。

### 4. 模拟与评估层 `battle/` + `reasoning/`

负责估算行动后果。

可分三步迭代：

1. **启发式评估**：根据属性克制、速度、HP、换入安全性给分。
2. **简化回合模拟**：估算伤害区间、状态变化、资源交换。
3. **分支搜索**：枚举双方候选行动，形成博弈树。

### 5. 博弈推理层 `reasoning/`

目标是回答：

- 我方最稳操作是什么？
- 我方高收益操作是什么？
- 对方最可能怎么应对？
- 如果对方读换，我方是否亏？
- 当前胜利条件是什么？

建议评估维度：

- 即时伤害收益
- 换入安全性
- 速度控制
- 队伍资源消耗
- 关键宝可梦存活价值
- 是否推进胜利条件
- 被反读时的最坏情况

### 6. 自然语言解释层

将结构化推理结果转成用户可读答案。

推荐输出格式：

```text
推荐操作：使用 XX 招式
理由：...
主要收益：...
主要风险：...
对方可能操作：...
备选方案：...
```

## 数据流示例

```text
用户：当前我方新叶喵 70% HP，对面水主 60% HP，该点什么？

解析：
- 己方在场：新叶喵，HP 70%
- 对方在场：水属性对手，HP 60%
- 可选行动：草本攻击 / 换人 / 变化招式

系统：
- 判断属性优势
- 估算击杀线
- 判断对手是否可能换入抗草宝可梦
- 输出稳定操作与读换操作
```

## 风险点

- 宝可梦真实规则复杂，不能一开始追求全量准确。
- 不同世代、规则、平台环境差异大，需要在输入中明确规则集。
- 对方配置不确定时，要以假设和概率方式表达。
- LLM 可能产生幻觉，需要让结构化规则层承担事实判断。
