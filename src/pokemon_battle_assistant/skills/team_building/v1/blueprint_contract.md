# 蓝图输出契约（planner 阶段）

你将收到：用户的建队需求（自然语言）+ 目标赛制。

你的任务：把需求解析成一份"队伍蓝图"——最多 6 个角色位，每个位描述一类需要的宝可梦（不是具体哪只）。

## 输出格式（纯 JSON，无 markdown 包裹）

```json
{
  "strategy": "一句话中文战术主线（如：晴天下高速特攻压制，九尾开晴，火系核心输出）",
  "slots": [
    {
      "role_zh": "角色位中文名（如：日照启动手）",
      "types": ["Fire"],
      "abilities_preferred": ["日照相关特性如 drought 可留空"],
      "stat_min": {"spe": 90},
      "stat_focus": ["spa", "spe"],
      "notes": "补充说明（中文，可空字符串）"
    }
  ]
}
```

## 字段规则

- `slots`：3~6 个角色位；核心位在前；
- `types`：该位偏好的属性（英文首字母大写，如 "Fire"、"Water/Dragon" 拆成两项）；无偏好给 `[]`；
- `stat_min`：硬门槛，键 ∈ {hp, atk, def, spa, spd, spe}（小写），值 0~255；无门槛给 `{}`；
- `stat_focus`：希望数值突出的维度（用于池内排序），1~2 项；
- `abilities_preferred`：可选，期望特性名（英文，如 "drought"）；不强求匹配；
- 不要在蓝图中指定具体宝可梦或具体招式——那是下一阶段的事。

## 蓝图设计要点

- 天气/空间/盾格等战术轴心的"启动位"必须与"利用位"成对出现；
- 留 1 个"自由位"（types=[]，stat_min={}）处理需求没覆盖到的联防缺口；
- 用户需求激进→偏重进攻数值；需求保守→补受盾位。
